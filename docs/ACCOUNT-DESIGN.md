# ระบบบัญชีและข้อมูลส่วนตัว — แบบเตรียมพัฒนา

สถานะ: ออกแบบแล้ว ยังไม่ได้เปิดระบบบัญชีจริงหรือเปลี่ยนข้อมูลของผู้ใช้

## ความต้องการที่ยืนยันจากผู้ใช้

- ปุ่มเข้าสู่ระบบพร้อมไอคอนบัญชี อยู่มุมขวาบนทั้งคอมพิวเตอร์และมือถือ
- มีหน้าเข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสผ่าน
- มีลืมรหัสผ่าน
- ข้อมูลทั้งหมดของผู้ใช้ต้องผูกกับบัญชีของคนนั้น

## รูปแบบการใช้งาน

1. เข้าสู่ระบบ: ชื่อผู้ใช้, รหัสผ่าน, ปุ่มแสดง/ซ่อนรหัสผ่าน, ลืมรหัสผ่าน, ลิงก์สมัครบัญชี
2. สมัครบัญชี: ชื่อผู้ใช้ที่ไม่ซ้ำ, ชื่อที่แสดง, อีเมลสำหรับยืนยันบัญชี/กู้รหัสผ่าน, รหัสผ่านและยืนยันรหัสผ่าน
3. ลืมรหัสผ่าน: ส่งลิงก์หมดอายุไปยังอีเมลที่ลงทะเบียน แล้วตั้งรหัสผ่านใหม่ ไม่ส่งรหัสผ่านเดิมกลับ
4. หลังเข้าสู่ระบบ: ปุ่มมุมขวาบนแสดงชื่อบัญชี พร้อมออกจากระบบ และสถานะซิงก์
5. โหลดข้อมูลบัญชีจากเซิร์ฟเวอร์ก่อนเปิดให้แก้ไข ไม่ดึงข้อมูลของ guest ไปทับบัญชีโดยอัตโนมัติ

## แนวทาง backend ที่เสนอ

ใช้ Supabase Auth ร่วมกับ PostgreSQL และ Row Level Security โดยเว็บยังเผยแพร่บน GitHub Pages เดิม

- Auth ดูแลการเก็บ hash รหัสผ่าน การยืนยันอีเมล session และ reset token
- username เป็นค่าเฉพาะของบัญชี ไม่เปลี่ยนข้อกำหนดให้ต้องเข้าสู่ระบบด้วยอีเมลอย่างเดียว
- endpoint ฝั่งเซิร์ฟเวอร์ใช้ค้นหาชื่อผู้ใช้เพื่อส่งต่อการยืนยันรหัสผ่านกับ Auth ไม่เปิดรายการชื่อผู้ใช้/อีเมลทั้งหมดต่อสาธารณะ
- จำกัดความถี่การพยายามเข้าสู่ระบบและกู้บัญชี แสดงข้อความผิดพลาดที่ไม่ยืนยันว่าบัญชีใดมีอยู่
- ฐานข้อมูล routine_data ผูก user_id กับ auth.uid() และบังคับสิทธิ์อ่าน/เขียนบนเซิร์ฟเวอร์ ไม่เชื่อ user_id ที่ client ส่งมา
- เก็บ routine state JSON ที่ผ่านการตรวจ schema พร้อม revision และ updated_at
- บันทึกแบบตรวจ revision ป้องกันการแก้ไขจากหลายเครื่องทับกันโดยเงียบ ๆ

## ข้อมูลที่ต้องบันทึกต่อบัญชี

ข้อมูลร่างกายและค่าตั้งต้น, แผน/ประวัติน้ำและเครื่องดื่ม, อากาศ/กิจกรรมรายวัน, ตารางชีวิต, มื้ออาหารและสารอาหาร, แผนออกกำลัง/สถานะทำแล้ว, ดูแลตัวเองเช้า/บ่ายและรายการเพิ่มเอง, โน้ต และประวัติทุกวันที่บันทึก

รูปอาหาร รหัสผ่าน API keys และรหัสเข้าใช้ Food AI ไม่รวมอยู่ใน JSON สำรองหรือข้อมูลกิจวัตรของบัญชี

## การรักษาข้อมูลเดิม

- guest เดิมใช้คีย์ jai-daily.v1 ต่อไป และไม่ถูกลบตอนสมัคร/เข้าสู่ระบบ
- cache ของแต่ละบัญชีแยก namespace จาก guest และบัญชีอื่น
- บัญชีใหม่ให้ผู้ใช้เลือกเริ่มข้อมูลใหม่ หรือนำเข้าข้อมูลเดิมในเครื่องอย่างชัดเจน
- หากดึงข้อมูลกลางไม่ได้ ต้องไม่แทนที่บัญชีด้วยข้อมูล guest และไม่อ้างว่าซิงก์สำเร็จ
- หากบันทึกชนกัน ให้เก็บฉบับในเครื่องและมีทางส่งออกสำรอง ก่อนเลือกรับข้อมูลกลางหรือนำการแก้ไขกลับมาใช้
- ออกจากระบบต้องล้าง session และกลับไป guest โดยไม่แสดงข้อมูลของบัญชีก่อนหน้า

## ตำแหน่งโค้ดที่วางไว้

- 01_web_app/src/pages/10_account — หน้าเข้าสู่ระบบ สมัคร กู้บัญชีและเปลี่ยนรหัสผ่าน
- 01_web_app/src/shared — auth client และการเชื่อม state/sync
- 04_account_backend — SQL migration, RLS, endpoint ชื่อผู้ใช้ และเอกสารตั้งค่า
- 03_tests — ทดสอบ auth, การแยกบัญชี, session หมดอายุ, sync/offline/conflict และการรักษา guest

โฟลเดอร์ใหม่ข้างต้นจะเพิ่มเมื่อเริ่มพัฒนาโค้ดจริง ไม่สร้างโฟลเดอร์ว่างเป็นส่วนที่อ้างว่าใช้งานแล้ว

## ข้อมูลภายนอกที่ยังต้องเชื่อม

ยังไม่พบ Supabase project หรือค่าตั้งระบบบัญชีใน repository/environment ที่เข้าถึงได้ จำเป็นต้องมี project ภายใต้บัญชีที่ผู้ใช้ควบคุม, URL/public publishable key, ฐานข้อมูล/RLS, endpoint ที่ deploy แล้ว, URL redirect ที่อนุญาต และบริการส่งอีเมลสำหรับยืนยันบัญชี/ลืมรหัสผ่าน

ไม่ขอรหัสผ่านส่วนตัวของผู้ใช้ และไม่ใส่ service-role/secret key ลง GitHub หรือหน้าเว็บ

## การตรวจรับก่อนประกาศว่าเสร็จ

- username/password เข้าสู่ระบบได้จริง และมีข้อมูลแยกผู้ใช้บนฐานข้อมูลจริง
- บัญชี A อ่านหรือเขียนข้อมูล B ไม่ได้ แม้แก้ request เอง
- สลับ guest/A/B, รีโหลด, ออกจากระบบ, token หมดอายุ ไม่ทำให้ข้อมูลปนกัน
- แก้ไขข้อมูลสองเครื่องแล้วไม่เขียนทับโดยเงียบ
- reset link ใช้ได้เฉพาะตามอายุ/เงื่อนไขของ Auth และตั้งรหัสใหม่ได้
- ทดสอบส่งอีเมลจริงและสองอุปกรณ์เมื่อ service พร้อม แยกผลทดสอบจำลองออกจากผลตรวจจริง
